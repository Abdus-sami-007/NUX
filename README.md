# TRAFFIC-X

## AI Urban Traffic Intelligence, Network Digital Twin & Counterfactual Simulation

TRAFFIC-X is a **software-only AI urban traffic intelligence and counterfactual simulation platform** designed for a Hyderabad-like urban road environment.

It uses the supplied traffic, network, incident, context, roadwork, signal-plan, turn-restriction, OD-demand, and planning-candidate datasets to:

- reconstruct the current traffic-network state,
- detect and classify supported congestion/incidents,
- forecast traffic conditions at **15, 30, 45 and 60 minutes**,
- estimate congestion spillback and propagation,
- evaluate aggregate OD-aware diversion scenarios,
- identify recurring bottlenecks,
- evaluate planning candidates through counterfactual simulation,
- provide evidence, uncertainty and limitations for important outputs.

---

# 1. Operational Boundary

> **All actions, diversion plans, traffic-management responses, construction/network suggestions, capacity changes and signal-plan changes generated by TRAFFIC-X remain simulated or advisory only.**

TRAFFIC-X does **not**:

- directly control traffic signals,
- access live cameras,
- integrate with GPS devices,
- integrate with roadside sensors,
- access municipal infrastructure,
- control vehicles,
- modify real roads,
- perform actual construction,
- execute real-world diversion plans.

For judging, the system operates using the **supplied dataset, chronological replay and scenario simulation**.

---

# 2. Why TRAFFIC-X?

Traditional traffic dashboards mainly answer:

> **What is happening now?**

TRAFFIC-X is designed to answer a broader decision-support sequence:

> **What is happening? Why is it happening? What is likely to happen next? How could it propagate? What would happen if we simulated an intervention?**

The core loop is:

```text
OBSERVE
   ↓
DIAGNOSE
   ↓
FORECAST
   ↓
PROPAGATE
   ↓
SIMULATE
   ↓
COMPARE
   ↓
EXPLAIN
```

# 4. Continuous Update / Replay

The dataset has **5-minute resolution**.

TRAFFIC-X supports chronological replay so that the application behaves like a continuously updating traffic-intelligence system without requiring live infrastructure.

```text
10:00 observations
       ↓
Update state
       ↓
Detect
       ↓
Forecast
       ↓
Propagate
       ↓
Refresh dashboard
       ↓
10:05 observations
       ↓
Update again
       ↺
```

The system must never use future observations when generating the current state or forecast.

# 5. Network Digital Twin

The Network Digital Twin is the software representation of the road network.

It combines:

- road segments,
- nodes,
- lanes,
- capacity,
- free-flow speed,
- current traffic,
- congestion,
- incidents,
- roadworks,
- signal metadata,
- turn restrictions,
- OD demand.

The network contains:

- **436 segments**
- **120 nodes**

The road network is represented as a directed graph:

```text
source_node → target_node
```

# 7. Data Preprocessing

The dataset intentionally contains realistic data-quality issues.

The preprocessing pipeline handles:

- missing values,
- duplicates,
- impossible values,
- traffic spikes,
- stuck sensors,
- low-quality observations,
- invalid readings.

The pipeline records whether observations are:

```text
VALID
IMPUTED
REPAIRED
REJECTED
UNAVAILABLE
```

This allows data quality to be included in confidence handling.

- delay,
- queue length,
- congestion index,

- sensor quality.

Possible UI states:

```text
NORMAL

CRITICAL
ABNORMAL

```

Thresholds should be calibrated from the training distribution rather than arbitrarily chosen.

# 9. Incident & Anomaly Detection

Incident data is joined to traffic observations using time intervals.

The system distinguishes:

```text
OBSERVED INCIDENT
TRAFFIC ANOMALY
POSSIBLE CAUSE
UNKNOWN CAUSE
```

An accident or other incident must not be claimed solely because congestion increased.

The baseline anomaly approach can use **Isolation Forest** together with explicit incident records and traffic evidence.

# 11. Spillback / Propagation Engine

The Propagation Engine estimates how congestion or disruption can affect connected segments.

It combines:

- directed network topology,
- upstream/downstream relationships,
- current traffic,
- capacity,
- forecast state,
- incidents,
- roadworks,
- aggregate OD demand.

Example:

```text
Incident
   ↓
Affected segment
   ↓
Upstream congestion
   ↓
Alternative-route demand
   ↓
Secondary congestion
```

Propagation results are labelled as estimates/simulations where appropriate.

---

# 12. Advisory & Diversion Simulation

TRAFFIC-X does not provide individual real-world navigation.

It evaluates **aggregate OD demand**.

The process is:

```text
Affected segment
      ↓
Identify impacted OD flows
      ↓
Generate feasible alternatives
      ↓
Apply turn restrictions
      ↓
Check capacity
      ↓
Simulate demand reassignment
      ↓
Calculate network impact
```

All diversion plans are:

> **SIMULATED / ADVISORY ONLY**

---

# 13. Counterfactual Engine

The Counterfactual Engine answers:

> **What would happen if we changed something in the network?**

It creates a simulated copy of the baseline network and applies a hypothetical intervention.

Possible scenarios include:

- incident,
- road closure,
- capacity reduction,
- roadwork,
- demand surge,
- OD diversion,
- alternative signal plan,
- planning candidate.

The system compares:

```text
BASELINE
     vs
COUNTERFACTUAL
```

using:

- average speed,
- total delay,
- travel time,
- queue,
- congestion,
- affected segments,
- network spillover.

---

# 14. Recurring Bottleneck Analysis

Recurring bottleneck analysis operates on **historical traffic data as a separate branch**.

It does not depend on the current live/replay forecast.

Indicators include:

- congestion frequency,
- congestion severity,
- duration,
- peak recurrence,
- structural bottleneck information,
- incident/roadwork-adjusted persistence.

```text
Historical Traffic
       ↓
Recurring Bottleneck
       ↓
Planning Candidate
       ↓
Counterfactual Simulation
       ↓
Before / After Impact
```

Each candidate can include:

```text
candidate_id
target_segment
intervention_type
capacity_delta_vph
```

The system evaluates candidates through simulation.

It does **not** claim:

- that construction occurred,
- that a project is approved,

All planning outputs remain **advisory**.

## Preprocessing robustness

- missing-value handling,
- imputation,
- outlier handling,
- duplicate detection,
- stuck-sensor detection,
- invalid-value handling.

## Stress testing

The system should test:

```text

10% data dropout
20% data dropout

Lower demand
Baseline demand
Higher demand

Sensor spikes
Stuck readings
Invalid readings

Unseen temporal/scenario conditions
```

Performance degradation should be measured rather than simply claiming robustness.

# 30. Final Principle

TRAFFIC-X is not designed to control the city.

It is designed to create a **safe software environment for understanding, forecasting and testing traffic decisions before they are considered in the real world**.

> **Observe → Diagnose → Forecast → Propagate → Simulate → Compare → Explain**

All operational actions remain **simulated or advisory only**.
